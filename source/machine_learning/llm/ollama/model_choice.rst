.. _model_choice:

==================
模型选择
==================

.. note::

   本文整理一些我准备采用的模型说明，针对我现有的硬件架构:

   - **3块** :ref:`tesla_a2` (16GB)总计48GB显存，单卡显存带宽200GB/s(极弱) ，支持 :ref:`tesla_a2_structural_sparsity`
   - **2块** :ref:`amd_mi50` (32GB) 总计64GB显存，单卡显存带宽(1.02TB/s)惊人 ，但 **没有** ``INFINITY FABRIC LINK 桥接器`` 连接情况下受限于主板PCIe 3带宽

   选择和说明综合gemini以及网上资料，不一定准确，后续会逐步补充更新

3块 :ref:`tesla_a2` 配套
============================

``qwen3-coder:30b``
----------------------

- **模型参数与架构** : ``30B`` 参数的 MoE（混合专家）模型，每次推理仅激活约 ``3.3B`` 参数。
- **显存占用** : Q4 量化版约 ``19GB``
- 3x Tesla A2（48GB）选择原因:

  - 极高的推理吞吐量：:ref:`tesla_a2` 的单卡显存带宽（约 ``200 GB/s`` ）并不算特别宽裕，如果跑全量激活的稠密（Dense）大模型，生成速度会偏慢。而 ``qwen3-coder:30b`` 的 **MoE** 架构每次只激活 ``3.3B`` 参数，在三张 A2 上能跑出极其丝滑的 Token 生成速度，非常适合日常高频代码审查与问答。
  - 超长上下文空间: ``48GB`` 总显存减去 ``19GB`` 模型权重，还剩下接近 ``29GB`` 的富余显存。这意味着可以把它的 ``256K`` 上下文窗口 拉满（设置 ``num_ctx: 65536`` 甚至更高），一次性把整个 Go/Python 微服务的核心文件塞给它做跨文件架构分析，而完全不会触发显存溢出（OOM）或掉回 CPU 内存。

``qwen3.8:27b``
-------------------

- **模型参数与架构** : 27B 稠密 (Dense) 架构
- **显存占用** : Q4 量化版约 (17GB-18GB) ，甚至可以跑 ``Q8_0`` 几乎无损量化版(约28GB-30GB)
- 3x Tesla A2（48GB）选择原因:

  - 稠密模型在复杂逻辑推理、并发锁排查、深度架构重构建议上通常比轻量级 MoE 更扎实。
  - 对于"自己写代码，仅在遇到棘手的Bug或者需要严格Code Review时由AI提建议"的开发模式，则建议使用更高精度的量化版本( ``qwen3.8:27b-q8_0`` )，利用三张 A2 的 48GB 显存换取接近原版 FP16 的代码逻辑精度。

``qwen3.8:27b`` 具体选择
~~~~~~~~~~~~~~~~~~~~~~~~~~

- 追求极致响应速度与大上下文: ``qwen3.8:27b-q4_K_M``

  - 占用显存约 18GB，在 3x A2（48GB）上可以非常从容地分摊，且剩余的大量显存能够完美支撑 ``64K - 128K`` 的超长上下文(KV Cache)    
  - 结合配置的 ``OLLAMA_KV_CACHE_TYPE=q8_0`` 和 ``Flash Attention`` ，这个组合在 A2 集群上跑起来如丝般顺滑，非常适合日常频繁的代码补全、多文件 RAG 检索和问答。

- 追求更高代码逻辑精度: ``qwen3.8:27b-q8_0``

  - 占用显存约 30GB: 48GB 总显存扣除后，还剩大约 18GB 留给 KV Cache(但是只够64K上下文)
  - 8-bit 量化对代码语法的严谨性、复杂并发 Bug 的推导表现比 4-bit 更扎实

- 可以尝试 ``-mtp`` 标签，通过压测对比一下在代码任务中生成速度是否有实际提升，因为部分 MTP 机制在复杂的本地非规律性代码编写时收益有限。

- 不可选择 ``-mlx`` 的标签(苹果Mac专用)

``flint:40b`` 或 ``devstral-small-2:24b``
------------------------------------------

- ``flint:40b`` : Recursive 出品，39.8B 的 MoE 代码专用模型，体积约 23GB，支持 256K 上下文与工具调用（Tool Calling）。在 48GB 显存下可以毫无压力地运行，适合搭配 Aider 或 Continue 进行多步任务拆解。
- ``devstral-small-2:24b`` : Mistral 出品，24B 稠密模型，体积约 15GB，在 SWE-bench Verified（真实软件工程问题修复基准测试）中达到了 68.0% 的高分，专门针对代码库级（Repo-level）理解和 Diff 补丁生成做过深度优化。

2块 :ref:`amd_mi50` 配套
===========================

``qwen3-coder-next:q4_K_M``
----------------------------

2026年2月4日阿里巴巴(Qwen团队)正式发布了开源权重编程智能体模型 Qwen3-Coder-Next。

核心规格与架构:

- 基础架构：基于 Qwen3-Next-80B-A3B-Base 构建，采用 Gated DeltaNet 与 Gated Attention 相结合的混合注意力（Hybrid Attention）与 MoE（混合专家）架构。
- 参数规模：总参数量约 80B，但单次推理激活参数仅约 3B（超低推理成本与极快运行速度）。
- 上下文窗口：支持高达 256K（262,144） 原生长上下文长度。
- 运行模式：仅支持非思考模式（non-thinking mode only）。
- 量化与部署：支持在消费级硬件上通过量化进行高效推理，适配 SGLang 和 vLLM 框架。

主要特点与能力:

- 专为 Coding Agent 打造：针对长程推理、复杂工具调用、执行失败恢复及全库（repository-scale）代码理解进行了强化训练。
- 生态兼容：开箱即用支持多种主流编码智能体和工具，如 Claude Code、OpenCode、Hermes Agent、OpenClaw、Cline 等。

从 Ollama 官网可以看到通过Agent模式加载 ``qwen3-coder-next`` ，我准备尝试一下agent是否真能实现较少的人工干预来完成软件开发。
