==========================
串流游戏(Game Streaming)
==========================

我一直在研究 :ref:`linux_desktop` 的远程实现方案，其中 :ref:`sunshine` 适合大型三维软件运行的架构，实际上是从 串流游戏(Game Streaming) 衍生出来的。

所谓“串流游戏”（Game Streaming），简单来说就是： **游戏在“后台强劲的电脑/服务器”上运行和渲染，而你在“轻量化的终端（如老旧MacBook、手机、电视盒）”上进行操作和观看。**

它的核心逻辑非常像“高实时性、带操作反馈的互动视频直播”。你手里的终端不需要有强大的显卡和 CPU，只需要具备两个能力： **能解码播放视频、能把按键信号发出去。**

串流游戏的工作流程与架构原理
================================

串流系统的整体架构可以拆分为四个核心环节，形成一个极速循环的闭环:

.. literalinclude:: game_streaming/infra
   :caption: 串流系统的架构

- **渲染(Rendering)** : 服务端运行游戏，显卡(GPU)渲染出游戏画面并输出音频。
- **实时编码(Real-time Encoding)** : 显卡内置的硬件编码器(如 NVIDIA NVENC、AMD AMF 或 Intel QuickSync)捕获渲染好的画面，以极高的速度将其压缩打包成 H.264、HEVC (H.265) 或 AV1 的视频流。
- **低延迟传输与解码(Transport & Decoding)** : 视频流通过局域网(或互联网)实时发送到客户端，客户端通过 GPU 的硬件解码引擎(如 VA-API)将视频解包，瞬间刷新在屏幕上。
- **控制指令回传(Input Forwarding)** : 在客户端按下的键盘、鼠标或手柄操作，被捕获后打包成极小的 UDP 动作数据包，瞬间传回服务端，驱动游戏中的角色做出反应。

串流的核心技术挑战：延迟(Latency)
======================================

串流游戏要求网络与处理总延迟控制在 ``10~30 毫秒(ms)`` 以内，否则人眼和手感就会察觉到明显的"粘手感"或卡顿。

为了保障这种极致的低延迟，串流架构采用了以下关键技术:

- **零拷贝与硬件编解码(Zero-copy HW Pipeline)** : 画面从显卡渲染出来后，直接在显存内部送入硬件编码器(如 NVENC)，不经过 CPU 和内存中转；客户端接收到视频包后，也直接送入 GPU 解码器(如 VA-API)输出，全程极致压缩时间。

- **低延迟传输协议(UDP-based Protocols)** : 串流协议(如 :ref:`moonlight` 使用的 GameStream 协议、 :ref:`sunshine` / RTSP 协议)普遍采用 UDP 传输，遵循"宁可丢弃个别画面帧，也绝不丢帧重传导致卡顿"的原则。

常见串流架构分类
==================

根据服务端位置的不同，串流分为两大主流模式:

- **局域网串流(Local Streaming)** :

  - 代表软件：:ref:`moonlight` + :ref:`sunshine` 、Steam In-Home Streaming、Parsec
  - 特点: 在同一个 Wi-Fi 或局域网内，延迟极低(通常 5~15ms)，画质极高，完全免费。

- **云游戏(Cloud Gaming)** :

  - 代表服务：GeForce NOW、Xbox Cloud Gaming (xCloud)、PS Remote Play(广域网)。
  - 特点：服务端在几百公里外的机房数据中心，按月付费。对客户端网络带宽和稳定性要求极高。
