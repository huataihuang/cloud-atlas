==========================
《Google SRE》概述
==========================

Google最早提出SRE(Site Reliability Engineering)，将传统的运维角色提升到现代大规模自动化运维的层次，也为我们开拓了观察、评估和持续改进系统稳定性的视角。

系统架构与稳定性防线(设计期 & 运行期)
========================================

- 简单性优先(Simplicity)

  - 复杂性是可靠性的隐形税负: 主动删减冗余逻辑、过度抽象与不必要的状态，降低高压下的排障推理成本。

- 自动化演进与发布工程

  - 发布原则: 封闭构建(Hermetic Builds)、高频小批量发布、渐进式灰度（金丝雀）与一键快速回滚。
  - 自动化原则: 追求幂等性、一致性校验与安全兜底，将一次性的救火脚本沉淀为可长期维护的平台工具。

.. note::

   "幂等性、一致性" 是实现发布和回滚的无损关键!!!

- 负载均衡与过载保护

  - 前端依赖 DNS/Anycast/边缘健康检查做地域与容量调度
  - 数据中心策略 "网络局部性" (Locality)，及时提出亚健康实例: 服务之间的调用尽可能发生在"物理距离最近、网络跳数最少"的节点之间，优先消化在本地或同一局部区域，非必要不跨机架、跨可用区（AZ）或跨地域转发流量。 **局部过载或异常时** 负载均衡器才会自动将超出承载部分的流量"溢出"转发到跨机架、跨可用区甚至跨地域。
  - 主动过载丢弃(Load Shedding): 流量超过承载上限时，按优先级主动拒绝非核心请求，保住核心链路不被拖垮。

- 切断级联故障(防雪崩四件套)

  - 严格超时: 下游调用必须 **设定合理超时** ，防止线程与连接池耗尽。
  - 退避与抖动: 重试必须使用指数退避 + 随机抖动(Exponential Backoff + Jitter)，避免并发重试齐刷刷打挂恢复中的服务。
  - 重试预算(Retry Budget):限制全局重试比例，防止局部故障被无限放大。
  - 舱壁隔离: 隔离关键资源池与依赖，遏制故障横向传染。

- 关键状态与数据完整性

  - 分布式共识: 配置、租约、选主等核心元数据必须依托强一致存储（Paxos/Raft 族），严防脑裂。
  - 数据管道与读写一致: 批流管道需具备幂等重放与积压水位监控；端到端数据依靠校验和与定期恢复演练，确保“所读即所写”。

故障响应与值班治理闭环
========================

- 实用告警(Practical Alerting): 只针对“需要人立即介入、且不处理就会损害用户体验或消耗错误预算”的症状触发告警，彻底清理“狼来了”式的噪音。
- 结构化排障(Troubleshooting): 遵循 ``接报 → 分级 → 检查 → 诊断 → 测试验证 → 根治`` 的科学循环；善用阴性结果(Negative Results)排除无关路径，拒绝盲猜乱改。
- 事故指挥(Incident Management): 明确区分 IC（总指挥）、通讯官与执行调查人员，维护实时事故状态文档，严禁多人未经授权各自修改线上环境（Freelancing）。
- 无指责复盘(Blameless Postmortem): 不追究个人过失，深挖系统与流程为什么允许错误发生；复盘必须产出有明确负责人与截止日期的 Action Items 并长期跟踪故障趋势。

团队协作与组织演进
====================

- 保护深度工作时间: 通过轮值分工将计划外打断集中处理（Polarizing Time），减少上下文切换，守住工程师做架构改进的整块时间。
- 阶梯式新人培养: 通过系统拆解、补全过时文档、Shadowing（跟班值班） 逐步解锁生产权限，平滑过渡到独立 On-Call。
- SRE 介入模式升级: 从早期"上线前被动评审(PRR)"向"架构设计初期介入"演进，最终将监控、发布与防护能力沉淀为通用平台与框架，避免为每个服务重复造轮子。
