==================
编写代码
==================

再优秀的工程师、再密集的人工 Code Review，也无法在规模化后单靠"小心写代码"维持全局不变式；真正能规模化保障安全与可靠的，是把约束和能力沉淀进"框架、类型系统与公共库"中，让不安全的写法在接口层就难以表达或被编译器直接拦截。

为什么不能只靠"小心写代码"和"人工 Code Review"
================================================

**代码里一定会有 Bug** ，安全与可靠性无法靠上线后"打补丁"补齐，更不能把希望寄托在开发者永远保持 100% 警惕上:

- **人的注意力与上下文有限** : 跨函数调用链变长后，审查者很难在脑子里长期追踪"某个参数究竟是可信常量还是来自外部不可信输入"。
- **人工审查存在盲区与疲劳** : 审查者往往更关注新颖攻击面或密码协议设计，而对几百个模板的 XSS 转义检查、每个 RPC 的错误处理细节很容易产生审美疲劳。
- **Code Review 的真正价值** : 不在于抓出所有漏洞，而在于 **倒逼团队写出结构清晰、安全与可靠性属性"显而易见"的代码，并推动自动化检查落地。**

用"框架与类型系统"固化不变式
==============================

- 用强类型与安全原语挡住常见漏洞:

  - 例如防 SQL 注入，与其靠人工检查每条拼接字符串，不如使用像 ``TrustedSqlString`` 这样的类型设计——把"已参数化/可信构造"的假设编码进类型系统，让编译器自动校验。
  - 防 XSS、内存越界或错误重试同样如此: 把正确路径变成最顺手的默认接口，把危险操作变成需要显式绕过或根本无法构造的接口。

- 集中修复:

  - 当认证、授权、审计日志、加密、限流、指数退避重试等横切关注点集中在公共框架或库中时，一旦发现通用缺陷或新增防护规则，只需在框架层修复一次，就能惠及所有接入服务，避免各业务服务各自"手搓"出一堆零散 Bug。

- 不盲目自研基础密码/安全库:

  - 除非有极特殊需求，否则尽量复用成熟、经过广泛审计的库与框架，并持续跟进依赖更新。

控制技术债与善用语言特性
==========================

- **遏制技术债、适度重构** : 代码越堆越乱，不变式就越难推理；把保持代码简洁和适时重构纳入日常工程节奏，才能维持长期迭代速度。
- **选对工具并吃透语言特性** : 充分利用所选语言的类型系统、内存安全机制与工程工具链，让语言本身替你挡住一部分低级错误，而不是靠意志力硬扛。
