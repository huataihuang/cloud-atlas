==========================
调查系统
==========================

当系统出现故障、性能退化或疑似安全事件时，如何 **依靠结构化调查方法、可信日志与合适的访问控制把根因挖出来** 。

排查系统的步骤(启发)
=======================

- 观察现象
- 分析监控
- 假设和验证
- 复现和定因
- 修复代码

系统化排障方法与"马与斑马"的规模效应
=======================================

- 排障的两大前提:

  - 了解系统原本应该如何工作
  - 保持系统化思维: ``收集数据 => 提出假设 => 验证假设``

- 区分"马"与"斑马" (Horses vs. Zebras)

  - 日常排障优先考虑常见原因("马"): 但随着系统规模扩大、常见 Bug 被逐步消灭，原本万分之一概率的极端事件("斑马"，如单核指令异常、哈希碰撞、32 位整型溢出、动态链接器在海量共享库下的超线性加载耗时、长时压测下的缓慢内存泄漏)会变成高频可观测现象。
  - 同时别把所有诡异问题都甩锅给硬件，也别盲信单一模型 -- 要结合数据交叉印证。

- 校验和(Checksum)的作用域与成本权衡:

  - 校验和能防硬件与软件损坏，但要看算力代价(如 CRC 适合防随机比特翻转、开销低；密码学哈希针对对抗性篡改)以及校验覆盖范围。
  - 如果客户端读数据时，校验和只包住 ``Value`` 而不包住 ``Key`` ，服务端一旦错把别的 ``Key`` 对应的 ``Value`` 连带校验和一起返回，单看 ``Value`` 校验依然会"通过"；把 ``Key`` 与 ``Value`` 一起纳入校验范围，才能抓住这类错位 Bug。

- 留出不被打断的深度调查空间:

  - 复杂排障或安全调查往往需要连续数小时的专注推演: 重大事件中，把深度调查者从分秒必争的外部沟通/指挥噪音中适当隔离开，更容易保住推理连贯性。

故障调试 vs. 安全调查，以及日志与访问控制的权衡
===================================================

运维与安全交汇处的两个现实张力:

- **排障与安全调查的差异** : 常规排障侧重恢复服务与定位故障机制；安全调查还要考虑攻击者轨迹、证据完整性以及"过早动作是否会惊动或暴露调查意图"。
- **日志留存与访问控制的平衡** : 排障需要充足的日志、指标与调试信息，但"只读排查权限"同样可能被滥用或暴露敏感数据。因此日志系统本身也需要做好访问控制、敏感信息保护与高可用保障，做到既能高效调查，又不把日志库变成新的泄密或单点故障源。

启示
====

- **善用内核与系统可观测工具** : 像 ``slabtop`` 这类贴近内核内存与资源分配的观测手段，在遇到"指标异常但应用层看不出明显报错"的隐蔽内存/存储问题时往往能一针见血
- **校验范围要覆盖"关联身份与数据"** ： 无论是存储校验、消息传递还是状态同步，检查"校验和到底保住了哪一段边界"，能帮我们避开不少"校验通过但数据错配"的坑。
