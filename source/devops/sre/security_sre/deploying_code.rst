==========================
部署代码
==========================

广义的软件供应链、构建与部署
=============================

**软件供应链(Software Supply Chain)** :编写、构建、测试、部署

- 构建(Build): 任何把输入产物(Artifact，如源码提交、文件、包、镜像)转换为输出产物的过程；测试(Test)也可以看作一种特殊的构建，只是输出通常是“通过/失败”这样的逻辑结果。
- 部署(Deployment): 任何把产物指派并应用到目标环境的行为 -- 既包括推送二进制/容器镜像/系统或固件启动，也包括修改数据库 Schema、调整启动参数(Flag)，或发布软件包/镜像到仓库供下游消费。

供应链威胁模型
================

在加固供应链之前，先区分三类典型威胁源:

- **善意内部人员** : 可能无意中用本地未提交、未审查的改动构建产物，或误把测试/调试开关带进生产，或部署了含已知漏洞的旧版本。
- **恶意内部人员** : 试图超越角色权限提交后门、篡改配置或窃取凭据。
- **外部攻击者** : 入侵工程师工作站或账号，或利用 CI/CD 配置缺陷、恶意构建脚本、被污染的编译器/构建工具、泄露的签名密钥来投递篡改后的产物。

四大基础实践: 从"信人"转向"验物"
=================================

- 强制代码审查(Require Code Reviews):

  - 本质上是一种 **多方授权** : 单个人不能独自把未经审查的代码送进主干。审查必须强制且认真(避免流于形式"盖章")，并与自动化测试形成纵深防御。

- 高度依赖自动化并锁死旁路:

  - 尽量让自动化流水线完成构建、测试与部署，消除"在个人工作站手工打生产包"的随意性与篡改窗口
  - 供应链配置本身也要走"配置即代码 + 同行审查"；同时要封堵绕过流水线的旁路（比如直接 SSH 登录构建机或绕过评审改 CI 规则）。

.. note::

   我觉得只有完全实现自动化"CI/CD"才能杜绝无序变更，才能控制和实现生产系统的发布隔离、异常回滚。绝对不能掺入任何手工变更，否则会在未来出现不可预知的故障。

- 验证产物与来源，而不只是验证"是谁点的部署"

  - 光看发起部署的人是谁不够 -- 人可能手抖，账号也可能被盗。部署环境(如 Kubernetes 准入控制 / Binary Authorization)应当校验产物本身是否来自可信流水线、是否具备合法签名与溯源证明(Provenance)，并只允许在受审计的 Breakglass 情况下放行例外。

.. note::

   生产环境必须严格限制部署入口，并且只有授权合法签名和溯源证明的发布系统才能对线上进行变更。这对于防范攻击非常关键，绝不要给攻击者有多余的修改线上系统的入口。严格保护生产环境的变更服务系统!!!

- 向可验证构建与溯源策略演进

  - 在高安全要求下，仅靠信任"某台机器声称自己构建了它"还不够，进一步需要可验证构建(Verifiable Builds)与基于溯源信息(Provenance)的部署策略，并采用分阶段、可回滚的方式稳步落地这些控制。

关键点
=========

**把"生产可信"的判定权交给自动化流水线与准入校验，而不是靠人肉记忆或口头约定。**

- **消灭"本地手工构建 + 随手推镜像/改配置"** : 无论是容器镜像、系统镜像还是集群配置，尽量通过受控构建流水线产出不可变产物，再由部署侧校验摘要/签名后上线
- **为例外留出可审计的"破窗"** : 真正紧急排障时如果需要绕过常规准入，必须留下清晰审计记录，避免"为了省事把门禁整个关掉"。
