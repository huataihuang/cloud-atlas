=============================
设计权衡(Design Tradeoffs)
=============================

所有工程团队都会遇到的核心难题: **在功能需求、开发速度、成本预算、可靠性和安全性彼此冲突时，如何在系统设计早期做出合理的权衡。**

功能需求、非功能需求和涌现属性
=================================

- 功能需求(Feature / Functional Requirements)

  - 关注系统"能做什么"
  - 必须区分出关键需求(Critical Requirements)——不满足它产品就无法成立的底线功能。

- 非功能需求(Nonfunctional Requirements)

  - 涵盖安全性(谁在什么条件下能访问什么数据)、可靠性(SLO 指标、P95/P99 延迟、过载保护)以及研发与发布效率(Development & Deployment Velocity)

- 涌现属性(Emergent Properties)

  - 可靠性与安全性都是整个系统架构与开发运维流程交互后"涌现"出来的整体属性——它取决于服务如何拆分、组件之间的信任边界、依赖链路的强弱、编程语言与框架选择、以及监控与审计能力。

Google 设计文档(Design Doc)中的强制要求
========================================

为了避免团队在项目上线前夕才发现安全或可靠性硬伤，Google 在工程立项的 Design Doc 模板中强制要求工程师在写代码前回答六大维度的问题:

- 可扩展性(Scalability): 数据量或流量激增时如何扩容？当前硬件与资源配额瓶颈在哪里？
- 冗余与可靠性(Redundancy & Reliability): 局部数据丢失或短暂故障时怎么办？数据如何备份、恢复期间服务如何降级、能否只恢复缺失分片？
- 依赖考量(Dependency Considerations)： 上游依赖不可用时系统会怎样？启动强依赖哪些服务（例如 DNS 解析或本地时钟同步这类隐蔽依赖）？是否存在死锁般的循环依赖？
- 数据完整性(Data Integrity): 无论是用户误操作、应用 Bug 还是底层存储损坏导致的数据丢失，多久能发现、如何恢复？
- SLA 保障(SLA Requirements): 靠什么审计和监控机制来兑现承诺的服务等级？
- 安全与隐私考量(Security & Privacy Considerations): 推演最坏情况下的攻击路径与影响，列出已知漏洞或不安全依赖；即便认为系统没有安全或隐私风险，也必须白纸黑字写明理由，并尽早触发安全设计评审。

典型场景中的设计权衡
----------------------

- 支付处理服务(Payment Processing Service) -- 可用性 vs. 数据一致性/防欺诈: 

  - 偏重可用性时，系统倾向于快速放行交易、异步对账，但这可能让恶意套现或双花攻击得逞
  - 偏重安全与资金完整性时，必须引入强一致性校验、风控拦截与多方签名，但这会增加延迟，甚至在风控依赖挂掉时导致合法交易被阻断(Fail-closed)。

- 微服务框架(Microservices Framework) -- 功能迭代速度 vs. 平台级安全约束:

  - 如果每个业务团队各自实现鉴权、加密和日志，短期看迭代很快，但长期必然出现配置遗漏、依赖混乱和难以维护的攻击面
  - 把安全与可靠性能力下沉到统一的微服务框架和基础设施层（提供“默认安全”的基建），虽然前期框架设计投入大，但能同时提升全员长期研发速度与系统整体基线

"事后补救"代价极其高昂!!!
==========================

- **推迟安全与可靠性工作是人的自然倾向** : 因为功能需求直接对应业务交付，而安全和可靠在不出事时往往"看不见"。
- **后期"外挂"几乎不可能** : 安全与可靠性如同选择数据库模型或单体/微服务架构一样，属于地基级决策。如果早期接口边界不清、依赖盘根错节，后期靠堆砌测试或零敲碎打修 Bug 根本无法改变系统的脆弱本质。
- **危机下的仓促重构风险极高** : 等到真正发生安全入侵或大规模宕机时再在高压下重构底层架构，不仅成本翻倍，还极易引入新的致命故障。相反，早期在架构层把边界、依赖和默认安全打牢，反而能换来整个项目生命周期持续稳定的开发速度。
