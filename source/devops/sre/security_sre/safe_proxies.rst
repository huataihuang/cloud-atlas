========================
安全代理(Ssfe Proxies)
========================

对于已经在线上运行、很难大改底层代码的存量系统，如何在不破坏原有体验的前提下，把特权操作关进笼子，同时防住黑客入侵和工程师手抖？

Google 给出的核心架构模式就是 ``Safe Proxies`` (安全代理)，这也是 Google 内部 ``Zero Touch Prod`` (零接触生产环境) 战略的重要支柱(Google 评估发现，约 13% 的生产事故可以通过 Zero Touch Prod 预防或缓解)。

.. note::

   现代大型分布式系统要收紧登录权限，尽可能将线上变更和故障处理通过有限制的工具完成，通过不可变的基础设施叠加受审计和防错误的变更工具来完成(CI/CD)，避免传统的管理员ssh登录无限制的手工操作。

核心理念：用代理层收拢"特权入口"
==================================

在传统运维中，拥有高权限的 SRE 或管理员往往可以直接通过 SSH 连上服务器，或者用本地 CLI 直接调用生产接口。这种模式下，无论是外部攻击者拿到了管理员凭证，还是善意的工程师输错了参数，都能瞬间造成灾难性后果。

Safe Proxy 的解决思路:

- 阻断直连： 修改目标服务器/应用的配置，使其只接受来自安全代理的请求，彻底封死除紧急 Breakglass（破窗机制）以外的所有直接连接。
- 统一网关： 所有人类管理员和自动化脚本都必须通过安全代理发起请求（调用的是应用层 RPC，而非开放式的交互式 Shell）。
- 透明接口： 代理对外暴露与目标系统一致的 API，尽量减少对用户原有工作流的干扰，在转发前后完成鉴权、审批、限流与审计。

.. note::

   通过 Safe Proxy 能够限制哪些API(命令)能够通过，可以实现安全审计和控制。

安全代理带来的收益
===================

- 多方授权(MPA, Multi-Party Authorization): 对于高危操作(如删除数据、下线核心服务、重启大规模节点)，单人权限不再直接生效，代理会挂起请求，强制要求另一位有审批权限的同事(如 admin-leads)在线确认后才放行。
- 全量审计追踪(Administrative Usage Auditing): 每一次变更在什么时候、由谁发起、传了什么参数、由谁批准，全部在代理层集中留痕，不依赖各个底层工具各自写日志。
- 速率限制与渐进发布(Rate Limiting): 例如限制机器重启的并发速率，防止一条误操作指令在一秒内把整个集群全部打死，把故障的爆炸半径(Blast Radius)锁死在可控范围内。
- 兼容闭源/遗留系统: 哪怕底层是无法修改源码的第三方闭源软件或老旧系统，只要在前面套一层安全代理，就能无痛补齐细粒度 ACL、审批和日志能力。
- 安全能力集中演进: 新增风控策略或检测规则只需更新代理层，无需逐个改造后端成百上千个子系统。

其他对等的工具
================

实际上，开源社区以及很多互联网公司也采用了类似的 ``Safe Proxy`` 工具，但是可能形式不同。

举例，在阿里采用了一种集成了审计和审批流程的 **终端跳板机** :

- 所有线上ssh操作都必须在 **终端跳板机** 完成，所以每一个登录线上的操作人员都需要审批权限，操作命令有记录也有系统审计流程
- 高危命令自动触发阻断，如果必须执行，则自动发起审批流程，只有审批通过该高危命令才能在一段时间内允许该操作人员执行

最佳实践构想
===============

现代云原生、Kubernetes 和自建基础设施管理:

- 告别裸 SSH 和直接持有集群 cluster-admin kubeconfig: 无论是人还是 CI/CD 流水线，都不应该在日常操作中直接持有对生产节点的 Root 或全量写入权限。
- 命令白名单化与审批流: 把高危的 :ref:`kubectl` 、 :ref:`terraform` 或系统维护脚本封装进受控的中间层（如结合 Teleport、GitOps 审批流或自研 API 网关），把"自由发挥的 Shell 操作"变成"带审计、带限流、可单元测试的结构化 RPC 调用"。
