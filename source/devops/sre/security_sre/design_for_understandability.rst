===================================
面向可理解的设计
===================================

复杂系统工程中最深层的痛点: **当系统规模不断膨胀、交互路径越来越多时，人类如何依然能够准确推演它的运行行为与安全/可靠性底线？**

可理解性(Understandability) 是指具备相同技术背景的工程师，能够准确且有信心地推演两件事的程度 -- 系统的运行行为，以及系统的不变式(Invariants, 包括安全与可用性属性)。

"可理解性"是关键
==================

投入精力让系统保持可理解，本质上是对长期迭代速度(Sustained Project Velocity)的复利投资，具体体现在三个维度:

- **降低改出新漏洞或新故障的概率** : 每次加功能、改 Bug 或调配置，都可能打破隐含假设。系统越难理解，工程师误判副作用、踩中未文档化约束的概率就越高。
- **提升事故响应效率** : 出现安全入侵或线上故障时，能否迅速评估影响范围、遏制扩散并定位根因，高度依赖排障者对系统边界的清晰认知。
- **增强对安全与可靠断言的信心** : 测试只能覆盖有限的典型路径，无法穷举"所有可能输入或极端状态"。要证明某项安全或可用性属性在各种边界条件下依然成立，必须依赖可推演的系统不变式。

系统不变式(System Invariants)与"务实中间路线"
===============================================

系统不变式指的是: 无论外部环境如何变化、遭遇何种异常或恶意构造的输入，系统都必须始终成立的属性。

例如:

- 只有经过认证且授权的主体才能访问持久存储，且敏感操作必留审计日志；
- 跨越信任边界的外部输入在进入 SQL、HTML 或命令执行接口前必做校验/编码；
- 后端请求量与前端流量保持合理比例，超时会优雅降级，过载时返回过载错误而非雪崩崩溃，且无退避的重试风暴不会把后端打垮。

在验证不变式时，现实工程往往夹在两极之间:

- 一端是"只靠局部测试和抽查代码": 成本低，但"没有看到问题不代表没有问题"(Absence of evidence is not evidence of absence)，注入类、越权类缺陷极易藏在未覆盖路径中。
- 另一端是"形式化验证(Formal Verification)": 数学证明力极强(如微内核级别可耗费数十人年)，但对庞大且频繁演进的业务与基础设施系统来说代价过高。

Google 的务实中间路线： 通过面向可理解性的架构设计，让工程师能够用清晰、克制的架构推理去论证关键不变式是否成立——这在大型工程实践中性价比最高，也最能系统性减少常见漏洞与故障模式。

心智模型(Mental Models)与"极端工况失效"
===========================================

人在面对复杂系统时，天然会构建心智模型——忽略无关细节，用抽象模块来推演整体。 **但心智模型有一个致命盲区:平时好用的模型，在异常或极端状态下可能会突然失效。**

- 比如某服务在常规负载下吞吐随请求量平滑上升，一旦越过临界点进入内存抖动（Thrashing）或 GC 停顿，吞吐量反而急剧下滑。如果排障者还套用“线性扩容/正常负载”的惯性模型，就会被带偏方向。 => `2026年11月12日微软Microsoft 365多项服务发生大规模全球宕机 <https://www.reddit.com/r/sysadmin/comments/1xxiasy/microsoft_postincident_report_is_up_for_the/?tl=zh-hans>`_ :

  - 该故障时由三个多月前部署的修复补丁导致，实际上这个补丁是在较差的测试硬件上测试，没有发现在拥有更多核心和更新硬件的机器存在争用死锁问题。也就是说大家默认的更好硬件表现更好在某些特定高并发场景是相反甚至很容易出现断崖式雪崩。
  - 该故障还暴露了长期潜伏的bug的补丁极难回滚，常规的故障切换实际上会导致压力过大从而出现大范围雪崩。

- 设计新组件时，它的行为与心智模型应尽量贴近团队已熟悉的同类子系统；同时 **在极端工况下也要保持可预测性** (例如生产节点禁用磁盘 Swap 避免内存抖动陷入泥潭，宁可快速失败并明确暴露内存压力，也不要让系统进入混沌难测的僵死状态)。 => 我忽然想到 :ref:`kubernetes` 设计中故意不引入节点swap，而是让Host主机内存耗尽时直接杀掉pod避免系统使用swap后性能抖动

控制复杂度:分层架构、统一框架与安全边界
=============================================

面对系统演进中不可避免的复杂度(如大型邮件系统、跨多服务微服务或大规模集群)，强调要对抗"不受控的复杂度(Unmanaged Complexity)"

- 分层与标准化框架: 身份认证、授权校验、访问控制和审计日志不要让每个业务或脚本各自“手搓”一套，而是下沉到统一、标准化的基础设施框架中，减少重复造轮子和配置遗漏。
- 明确的安全边界(Security Boundaries): 清晰划定哪些组件处于同一信任域、哪些属于跨边界调用，在边界处集中完成校验与隔离，避免权限与信任关系像意大利面条一样缠绕。
- 收敛 API 与框架设计: 接口与框架越克制、越符合直觉，越容易让人看清"数据从哪里来、权限如何传递、失败时会落到哪一步"。
