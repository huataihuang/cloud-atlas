============================
测试代码
============================

测试代码的关键点: 如何在代码进入生产环境前，用多层次的测试与分析手段尽量把边界条件、异常输入和隐藏 Bug 提前揪出来。

无论多么谨慎，遗漏的边界条件与错误都不可避免
==============================================

- 非预期输入组合可能触发数据损坏或"死亡查询(Query of Death)"式的可用性故障
- 编码缺陷可能演化为缓冲区溢出、越权或 XSS 等安全漏洞
- 尤其是那些不容易快速热修/紧急回滚的系统，更需要在上线前投入充分的测试与验证。
- 不同测试手段的成本收益比不同，应根据阶段与风险合理组合。

单元测试:快、稳、隔离(Hermetic)与"测对东西"
==============================================

单元测试是本地开发与 CI 门禁中最基础的一环，要让它真正发挥安全与可靠性价值:

- 隔离性与确定性(Hermeticity): 单元测试应摆脱外部真实依赖，每次运行结果可重复。一旦测试出现"时好时坏(Flaky)"，工程师就会开始习惯性忽略测试结果，测试防线就会形同虚设。
- 不只是测"正常路径": 除了功能正确性，还要主动测试安全与边界用例——比如存储配额系统中的负数申请、接近整型上限的溢出风险、畸形/恶意输入下的错误处理，以及权限边界校验(例如"只有特定账单管理员才能申请扩容")。
- 警惕"假测试"与过度抽象:

  - 可以通过变异测试(Mutation Testing)检验测试是否真的在约束逻辑(例如把 ``if (cond_1 || cond_2)`` 改成 ``if (true)`` 或 ``if (false)`` 后，测试是否会失败)
  - 在使用 Mock / Stub / Fake 隔离外部依赖时，避免把测试写得过于死板(比如机械断言内部调用顺序)，否则代码一重构测试就大面积报废；最好由依赖方维护更贴近真实行为的 Fake 实现。

正确性验证与集成测试
=========================

- 正确性测试集 (Correctness Validation) : 针对协议解析、格式转换或密码学实现，利用标准化测试向量和边界用例集(如密码学边界测试集、RFC 规范用例集)验证实现是否符合标准、是否能抵御已知攻击模式，也能用来检验替换实现后外部可观测行为是否一致。
- 集成测试(Integration Testing): 逐步替换掉 Fake/Stub，让组件与真实依赖或编排环境联动，验证端到端交互路径。代价是速度变慢、受网络延迟或环境状态影响更大，因此需要与快速单元测试分层搭配。

静态/动态分析与模糊测试(Fuzzing)
==================================

- **静态与动态程序分析** : 在代码未运行或运行时检查潜在缺陷、危险调用与异常行为
- **模糊测试** (Fuzzing) : 向目标接口或解析器灌入大量随机、畸形或变异输入，非常适合用来暴露解析器崩溃、内存/状态异常、信息泄露以及大量意想不到的边界条件。
