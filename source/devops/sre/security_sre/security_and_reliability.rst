==========================
安全性和可靠性的关系
==========================

SRE的原意是Site Reliability Engineering，也就是关注的核心是 ``Reliability`` 可靠性，但是随着技术的发展，原有的"可靠性"定义和范围已经极大地扩展了。

安全性和可靠性的核型差异: 有没有"恶意对手"
===========================================

安全和可靠都追求 **系统可信** ，但设计前提完全不同:

- 假设前提不同:

  - 可靠性（Reliability）： 面对的多是非恶意故障（硬件损坏、软件 Bug、配置失误、突发流量）。假设是“有些事情迟早会出错”。
  - 安全性（Security）： 面对的是有主观意图、会主动寻找薄弱环节并利用漏洞的攻击者（Adversary）。假设是“随时可能有人故意让系统出错”。

- 冗余的双刃剑:

  - 加冗余组件、备用路径或后备入口能提升可靠性，但同时会扩大攻击面（Attack Surface）——对防御者而言要守住所有路径，对攻击者而言往往只需打穿其中一条。

- 事件响应与信息共享策略不同:

  - 可靠性事故通常鼓励跨团队快速拉通、集思广益，尽快定位根因并恢复服务；日志越详尽越有助于排障。
  - 安全事件则必须严格遵循最小知情范围（Need-to-know），避免过早暴露调查进展或惊动攻击者；同时，过于详尽的日志如果落入攻击者手中，反而可能泄露敏感信息或帮助攻击者摸清防御盲区。

理解"对手"
------------

在可靠性语境下，“对手”通常是抽象且无恶意的（硬件老化、配置失误、突发流量、“成功灾难”乃至挖断海缆的渔船）；而在安全语境下，对手是有计算、有目的的人类。不理解两类“对手”的运作方式，就很难设计出真正具备生存力的系统。

除了“为什么打”和“谁来打”，系统工程师还需要理解攻击者“怎么打”——从前期侦察、获取立足点、横向移动与权限提升，到最终达成目标（窃取数据、篡改状态、破坏可用性或持久化驻留）。把攻击拆解成阶段性步骤后，防御者才能在各个节点设置检测点、缩小爆炸半径并阻断链路。

工程实践启示
----------------

- 按真实威胁面做设计，而不是按"平均水平"做设计: 如果你做的是内部普通工具，威胁模型可能主要是误操作与低门槛扫描；但如果你管的是核心认证、密钥、资金流转或高敏感数据，就必须假设对手具备极高的耐心、资金与隐蔽能力。

- 用"攻击者视角"审视系统假设: 设计系统时别只问"正常情况下组件怎么协作"，还要多问一句："如果某个组件被控制、某个凭据泄露或某个配置被篡改，攻击者会顺着哪条路径走到核心资产？"

安全性和可靠性的工程落地原则
=============================

- 涌现性与前置设计： 安全性和可靠性都是系统架构中多组件交互涌现出来的属性，很难在系统上线后再像打补丁一样“外挂”上去，最好从设计早期就一并考量，并在整个生命周期持续验证。
- 平时“隐形”，出事代价极高： 系统平稳运行时，安全和可靠的工作往往看不见，容易在预算或排期中被低估、延后；可一旦出事（如重大数据泄露导致收购估值缩水，或核心系统宕机导致大面积航班延误/取消），代价极其惨重。
- 风险评估与克制复杂度： 不可能追求绝对零风险或 100% 安全，需要结合业务成本与风险做权衡；而保持系统简洁（Simplicity）是同时提升可评估性、降低攻击面、减少意外交互以及加快故障排查（缩短 MTTR）最有效的方法之一。
