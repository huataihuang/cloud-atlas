=============================
面向最小权限的设计
=============================

系统的工程方法论: **如何让人类用户、自动化任务、机器节点以及各类工具，只拥有完成当前任务所必需的最小访问权限。**

核心出发点：不要假设"人不会出错"
====================================

一个现实工程盲区:很多团队在设计权限时，默认工程师是善意的、工具是可信的、操作是无误的。但现实往往是:

- 工程师可能敲错命令、复制粘贴失误，或者在紧急排障时手抖扩大影响范围
- 工程师的账号或工作站可能被钓鱼、恶意依赖或供应链攻击攻破 => `币安称黑客通过虚假工作面试入侵工程师笔记本电脑 <https://www.solidot.org/story?sid=85789>`_
- 少数情况下也可能存在内部滥用或恶意行为

因此，最小权限原则不能停留在口号，而要贯穿到认证、授权、工具链和运行时的每一个环节，重点消除两类高危状态:

- 隐式工具授权(Implicit Authority to Tooling): 工具不应默认继承调用者的全部特权，也不应盲目信任外部输入
- 常驻特权(Ambient Authority): 避免让日常运维人员或服务长期处于 root 或全局管理员状态

三大支柱理念: 最小权限、零信任与 Zero Touch
==============================================

- 最小权限(Least Privilege): 无论是人还是自动化组件，都只给"刚好够用"的权限，并在任务完成后及时收敛。
- 零信任网络(Zero Trust Networking): 网络位置不再等于信任(例如连上内网网线或处于某个网段，不应自动获得特权)。访问决策应结合用户身份凭证 + 设备可信状态动态评估(Google 对应的实践是 BeyondCorp)。
- Zero Touch(零接触): 尽量通过自动化工作流、受控 API 和多方审批来执行生产变更，减少人类直接登录生产环境执行高危命令的机会。

按风险分级控制权限
====================

不同数据和操作的风险等级完全不同，如果对所有资源采取同一套严苛审批，研发与排障效率会被拖垮；反之，全部放宽则会带来巨大隐患。

- 风险分级维度: 可以按数据敏感度或操作破坏力划分级别（例如公开/内部常规数据、敏感数据、高度敏感数据/密钥），并对读权限、写权限、基础设施控制权限分别评估风险。
- 安全与可靠的视角互补:

  - 从可靠性看，重点防的是误删任务、乱改 ACL、错误配置导致的服务中断
  - 从安全性看，"只读权限"同样危险——过宽的读取权限往往是大规模数据泄露的源头

关键工程实践
=============

尽量使用小而明确的功能性 API(Small Functional APIs)，而不是开放式的交互式接口:

- **管理面 API 的特殊风险** : 相比面向终端用户的 API，管理类 API（Administrative API）（如启停服务、修改配置、清理异常状态、扩缩容）往往权限更高、误操作后果更严重，也是攻击者最盯防的目标。
- **传统 SSH + 交互式 Shell 难审计、难约束** : 一旦开放交互式 Shell，调用者就拿到了整个 POSIX 接口的灵活能力，这是难以完整记录也是审计脆弱的
