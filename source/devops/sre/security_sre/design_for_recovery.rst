============================
面向恢复(Recovery)的设计
============================

面向恢复(Recovery): 当故障、异常或恶意入侵确实发生、系统需要回到健康状态时，如何提前在架构上做好准备，让恢复既快又稳，还不会顺便把旧漏洞"回滚"回来。

"恢复"充满隐蔽的 ``权衡``
=============================

恢复看似只是"把坏掉的系统修好"，但在真实生产环境里往往暗藏矛盾:

- 回滚(Rollback)可能带回安全漏洞: 为了止住线上稳定性故障，把版本回退到上一个稳定包，但如果上一个版本恰恰包含未修补的安全漏洞，就会重新暴露攻击面。
- 紧急修补(Hotfix / Patch)可能引发新的宕机: 高危漏洞被公开利用时，发布节奏必须加快以抢在攻击者前面，但测试时间被压缩，容易引入新的稳定性 Bug。
- **仓促清理可能惊动攻击者** : 在安全入侵场景下，过早重启机器或清理痕迹，不仅可能破坏取证线索，还可能向攻击者暴露防御方已察觉。

常见问题场景
===============

- **随机错误(Random Errors)** : 物理硬件老化或损坏(电源、网卡、磁盘、CPU 单核异常指令)、比特翻转、自然灾害或电网/UPS 波动。其中静默损坏(Silent corruption)最隐蔽、最难恢复。
- **意外错误(Accidental Errors)** : 善意但出错的人类操作。任务越复杂，人为失误概率越高；缺乏工程/流程安全护栏的单人操作尤其容易放大影响(此外还有挖断光缆这类外部施工意外)。
- **软件错误(Software Errors)** : 本质上是"延迟发作的人类设计/编码错误"。Bug 不仅会直接导致崩溃，有时还会模仿恶意攻击(例如缺乏安全校验的自动化脚本突然大面积修改生产状态)或放大其他异常。
- **恶意行为(Malicious Actions)** : 内部人员越权滥用、被社工/胁迫，或外部攻击者窃取凭据、控制供应链后发动的破坏与篡改。无论是"内鬼"还是"外部入侵者拿了合法凭据"，在系统架构防护思路上都需要一视同仁地加以约束。

核心设计原则:把"变更能力"与"变更速率策略"解耦
===============================================

架构建议: 让变更/恢复机制具备"尽可能快"的执行能力，但用外部策略(Policy)与独立限流来控制它的实际速度:

- **紧急发布系统 = 调高上限的常规发布系统** : 不要维护一套"平时用"的发布流程和另一套"应急用"的野路子流程。未经日常演练的应急通道，真到关键时刻往往靠不住。更好的做法是：平时按稳妥的节奏和速率限制推进变更；遇到 Heartbleed、ShellShock 或活跃入侵等突发情况时，只需调整速率/审批策略，就能让同一套成熟流水线跑出最快速度，同时保留回滚的同构能力。
- **把速率限制拆成独立、单一职责的微服务** : 既然底层变更执行能力可以很快，就需要一个尽量简单、可充分测试的独立限流组件来卡住发布节奏(例如签发短时效令牌、集中记录变更审计日志)。多一个依赖组件会增加一点复杂度，但换来的是"执行动作"与"变更速率控制"清晰解耦，也能避免工程师在各处私自写散乱的限流逻辑。
- **明确"已知良好状态(Known Good State)"与兜底路径** : 无论用回滚、版本号控制还是吊销机制恢复，都必须清楚系统要回到什么状态——以及 **当常规通道不可用时，如何安全地抵达良好状态。**

.. note::

   我感觉难度在于如何深刻的理解变更系统，作为基础设施SRE，系统变更是通过平台完成的，但是平台完成的原理以及完成步骤的具体操作一定要掌握在自己手里。也就是说，系统变更平台应该是基础设施SRE自己开发和维护的，你自己应该深刻了解变更是如何完成，以及在特殊情况下如何控制变更，甚至手工完成变更，以恢复到"Good State"。

经验
======

- 把"恢复路径"纳入常态化演练: 备份能不能恢复、镜像能不能回滚、配置能不能快速收敛，不能只看文档或理论，必须反复验证；否则故障发生时，恢复链路本身就会成为第二重瓶颈。
- 警惕"回滚即重开漏洞"与"盲目重启毁现场": 排查稳定性问题时看一眼版本安全基线；排查疑似入侵时先保全状态与证据，避免下意识重启或清理把线索冲掉。
