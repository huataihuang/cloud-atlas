============================
面向韧性(Resilience)的设计
============================

韧性(Resilience): 系统在遭遇严重故障或主动攻击时的"抗压与持续运行能力" -- 即便无法完全避免受损，也要让核心功能尽量维持可用，把影响锁在局部并加速恢复。

"韧性(Resilience)" 与 "恢复(Recovery)" 的区别
===============================================

- 韧性(Resilience): 侧重 **延缓或扛住破坏** 。当部分甚至整体系统遭遇异常压力或攻击时，系统能够自动稳住阵脚，往往以降级模式(Degraded Mode)持续提供服务，而不是一触即溃。
- 恢复(Recovery): 侧重 **损坏后的修复与重建**

两者配合才能做到少人工介入、快恢复!!!

对于规模较小的团队或初期系统，建议优先抓 **可控降级、爆炸半径控制与故障域隔离** ，随着规模扩大再逐步投入 **持续验证** 与 **自动化韧性能力** 。

构建韧性系统的六大设计原则
===========================

- **每一层都具备独立韧性** : 不把希望寄托在单层防御上，而是层层设防，形成纵深防御(Defense in Depth)。
- **评估功能优先级与资源成本** : 明确哪些是无论多大负载都必须保住的核心能力，哪些是次要功能，在资源吃紧或异常时果断限流、降级甚至关闭，把有限算力留给核心链路。
- **沿清晰边界划分区隔(Compartmentalize)** : 把独立功能拆进隔离的舱室/域中，互不牵连，也便于各自配置互补的防护策略。
- **分区冗余与差异化属性** : 局部故障靠分区冗余兜底；面对全局性问题时，让不同分区具备差异化的可靠或安全属性，避免"一损俱损"。
- **自动化缩短反应时间** : 把经过充分验证的韧性动作交给自动化，不断发掘新的故障模式去完善自动兜底逻辑。
- **持续验证韧性有效性** : 自动化与架构韧性不能只停留在图纸或首次上线，必须通过持续验证确认它们在真实压力与攻击下依然管用。

纵深防御
============

一次典型入侵拆解为四个阶段，每一层防线都能抬高攻击成本、争取拦截窗口:

- **威胁建模与漏洞发现** : 攻击者会踩点侦察、寻找薄弱点；防御者则要尽量减少对外暴露的信息，同时把端口/应用扫描、相似域名注册监控、威胁情报等侦察信号变成早期预警。
- **攻击部署** : 既然无法挡住所有外部探测与投递，就要在入口处做检查、隔离与执行控制(如流量检查、沙箱检测、异常权限告警)，不让可疑载荷轻易长驱直入。
- **攻击执行** : 假设个别攻击还是进来了，也要靠 **沙箱隔离(Sandboxing)** 与 **爆炸半径限制** 把活动范围死死框住，不让它横向扩散或拿到全局控制权。
- **失陷与处置** : 一旦发现失陷，后续响应速度决定了受损时长与代价。

Google App Engine 的多层隔离实践案例
=======================================

早期 Google App Engine 需要在一个共享基础设施上运行大量不可信的用户代码，如果每个用户都开独立虚拟机，成本与效率难以承受；但直接靠传统 POSIX 用户隔离又远远不够。于是团队采取了 **逐层收紧与沙箱兜底** 的策略:

- **收紧高危 I/O API** : 移除运行时中直接操作网络和本地文件系统的危险接口，替换为受控的安全接口；禁止用户上传编译后的字节码或共享库，避免绕过限制。
- **加固运行时并叠加双层沙箱** : 审计底层运行时数据结构以减少内存破坏漏洞，同时将 Python 运行时编译为 ``Native Client(NaCl)`` 字节码来防内存破坏与控制流劫持；再叠加 ``ptrace`` 沙箱拦截异常系统调用，一旦违规立即终止并高优先级告警。
